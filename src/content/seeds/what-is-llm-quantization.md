ChatGPT를 돌리는 서버에는 $30,000짜리 H100 GPU가 꽂혀 있다. 그런데 Llama 3.2 같은 오픈소스 모델은 맥북에서도 돈다. 파라미터 수가 수십억 개인 건 똑같은데, 어떻게?

답은 양자화(quantization)다. 모델을 압축하는 기술이다.

## 1. 메모리부터 계산하자

언어 모델은 "파라미터"라는 숫자 덩어리다. Llama 3.2 3B는 파라미터가 30억 개다. 각 숫자를 저장하려면 메모리가 필요하다.

```
파라미터 × bit 수 / 8 = 필요 메모리
```

기본적으로 모델은 FP32(32-bit float)로 훈련된다. 3B 모델이면:

```
30억 × 32 / 8 = 12 GB
```

추론할 때 중간 계산 버퍼까지 고려하면 실질 RAM은 15GB 이상. 16GB 맥북이면 빠듯하다.

FP16(16-bit)로 내리면 절반:

```
30억 × 16 / 8 = 6 GB
```

INT4(4-bit)까지 줄이면:

```
30억 × 4 / 8 = 1.5 GB
```

같은 모델이 8배 가벼워졌다. **이게 양자화다.** 숫자를 더 적은 bit로 표현해서 모델을 압축한다.

## 2. 직접 돌려보자

Ollama를 설치하면 양자화된 모델을 한 줄로 돌릴 수 있다.

```bash
brew install ollama
ollama serve &
ollama run llama3.2:3b-instruct-q4_K_M
```

`q4_K_M`이 양자화 설정이다. 4-bit 양자화, K-quant 방식, Medium 변형이다(뒤에서 설명).

같은 모델(Llama 3.2 3B)을 네 가지 양자화로 받아서 비교해봤다. Apple M4, 16GB RAM.

| 양자화 | 디스크 | 로드 메모리 | 속도 (tok/s) |
|---|---|---|---|
| Q2_K | 1.4 GB | 2.1 GB | 53.6 |
| Q4_K_M | 2.0 GB | 2.8 GB | 47.2 |
| Q8_0 | 3.4 GB | 4.2 GB | 30.1 |
| FP16 | 6.4 GB | 7.2 GB | 16.3 |

처음 보면 뭔가 이상하다. **압축할수록 빨라진다.** FP16이 가장 느리고 Q2가 가장 빠르다.

이유는 맥북의 구조다. Apple Silicon은 메모리 대역폭이 병목이다. 모델이 작을수록 매번 옮기는 데이터가 적어서 빨리 돈다. GPU 서버라면 계산량이 병목이라 덜 극적이지만, 맥북/모바일/임베디드에서는 양자화가 속도에도 직결된다.

## 3. 품질은 얼마나 떨어질까

같은 프롬프트를 네 모델에 똑같이 던졌다.

**프롬프트 1 (영어)**: "Explain quantum entanglement in exactly 2 sentences."

영어는 네 모델 모두 비슷하게 답했다. 어색함이 거의 없다.

```
Q2_K : Quantum entanglement is a phenomenon where two or more 
       particles become "entangled" and are connected...
Q4_K_M: Quantum entanglement is a phenomenon where two or more 
        particles become connected in such a way...
Q8_0 : Quantum entanglement is a phenomenon where two or more 
       particles become connected in such a way...
FP16 : Quantum entanglement is a phenomenon where two or more 
       particles become connected in such a way...
```

여기까지 보면 "오, Q2도 쓸만한데?" 싶다. 그런데 한국어로 바꾸면 얘기가 달라진다.

**프롬프트 2 (한국어)**: "한국의 수도를 한 문장으로 답하고, 대표적인 관광지 3곳을 간단히 소개해줘."

```
Q2_K:
  Korea의 수도는 서울입니다.
  1. 부석사원: 한국에서 가장 유명한 무기적 신비ン한 아들(BoSeok)입니다.
  2. 경-IN문(Kyong-Inmunse): 8월에 이달 29일까지는 연중을 해도 도전합니다.
  3. 양미사원(YangMiSa): 한수에서 우주를 한다.
```

말이 완전히 무너졌다. "무기적 신비ン한 아들"은 사전에 없는 단어 조합이고, "양미사원"은 존재하지 않는 절이다. Q2는 2-bit라 표현 가능한 값이 네 개뿐이라 한국어처럼 훈련 데이터가 적은 언어의 미묘한 분포를 담지 못한다.

```
Q4_K_M:
  한국의 수도는 Seoul입니다.
  1. 고대 사자원: 한국에서 가장 오래된 유적-site로...
  2. 기성산: 서울에 위치한 山으로, 한국의 고사자원 중 하나입니다.
  3. 마포대성전: 서울특별시 마포구에 있는 명상소로...
```

Q4는 문법은 맞지만 관광지 이름을 지어낸다("고대 사자원", "기성산", "마포대성전"). 이걸 환각(hallucination)이라고 부른다.

```
Q8_0:
  한국의 수도는 서울입니다.
  1. 경복궁: 한국의 전통 궁전이며, 조선 시대에 수년 동안 royal palace로 사용된 곳...
  2. 중산성: 서울의 역사와 문화를 보는 곳...
  3. 이천시: 한국 최초의 과학도원으로...

FP16:
  한국의 수도는 세우로, 대표적인 관광지는 경복궁, 제주도, 그리고 감시경이 있습니다.
  경복궁: 한강을 이웃한 경복궁은 한가로운 일상과 고고한 의식의 중심...
  제주도: 한국에 있는 유일한 tropical 섬...
```

Q8부터 "경복궁"이 나온다. FP16은 제주도까지 맞추지만 "세우", "감시경" 같은 가짜 이름은 여전히 섞인다.

여기서 두 가지를 배운다.

1. **양자화의 영향은 언어마다 다르다.** 영어는 Q2에서도 멀쩡했지만, 한국어는 Q8까지 올라가야 경복궁이 나온다. 훈련 데이터가 적은 언어일수록 양자화에 취약하다.
2. **환각은 양자화 탓만은 아니다.** FP16도 "감시경"을 지어낸다. 3B 모델 자체의 한계다.

## 4. 포맷이 여러 개인 이유

`q4_K_M` 외에도 GGUF, GPTQ, AWQ, bitsandbytes 같은 이름이 보인다. 헷갈리는데, 쓰임새가 다르다.

```
+-------------+-------------------+------------------------------+
| 포맷        | 주 용도           | 특징                         |
+-------------+-------------------+------------------------------+
| GGUF        | CPU/Mac 추론      | llama.cpp, Ollama가 씀       |
| GPTQ        | GPU 추론          | 엔비디아 GPU에서 빠름        |
| AWQ         | GPU 추론          | GPTQ보다 품질 우위           |
| bitsandbytes| 학습 + QLoRA      | 4-bit 파인튜닝의 표준        |
| EXL2        | GPU 추론 (고속)   | ExLlamaV2 전용               |
+-------------+-------------------+------------------------------+
```

맥북이면 GGUF만 알면 된다. `.gguf` 파일 하나에 모델 전체가 들어있고, Ollama/llama.cpp/LM Studio가 전부 이걸 읽는다.

GGUF 안에서도 세부 양자화 방식이 여러 가지다.

```
Q2_K   → 2-bit, 가장 작음, 한국어는 붕괴
Q4_K_S → 4-bit, Small (빠름, 품질 약간 낮음)
Q4_K_M → 4-bit, Medium (권장, sweet spot)
Q5_K_M → 5-bit, 품질↑ 크기↑
Q8_0   → 8-bit, FP16과 거의 같은 품질
F16    → 양자화 없음
```

일단 **Q4_K_M으로 시작하는 게 정석**이다. 영어 위주면 여기서 멈춰도 되고, 한국어가 중요하면 Q8_0까지 올리자.

## 5. 왜 4-bit가 sweet spot일까

여기서부터 내부 이야기다.

모델의 weight는 대부분 0 근처에 몰려있다. 정규분포 비슷한 모양이다.

```
         ██
        ████
       ██████
      ████████
     ██████████
    ████████████
  ─┼────┼────┼─
  -1    0    1
```

이 분포를 표현하려면 0 근처에 해상도가 많이 필요하다. 양 끝(outlier)은 드물지만 존재한다.

FP32는 전 범위를 과잉 정밀도로 표현한다. 실제 weight가 쓰는 범위는 좁다. 그래서 "필요한 범위만 잘라서" 낮은 bit로 매핑하는 게 양자화다.

문제는 bit 수다.

```
Q2 → 표현 가능한 값 4개   (2² = 4)
Q4 → 표현 가능한 값 16개  (2⁴ = 16)
Q8 → 표현 가능한 값 256개 (2⁸ = 256)
```

Q2는 값이 네 개뿐이라 분포를 거칠게 뭉갠다. Q4는 16개로 충분히 근사한다. Q8은 256개니까 FP16과 구분이 안 된다.

품질 곡선은 대략 이렇다.

```
품질
 │   ┌──────────── Q8, FP16
 │  ╱
 │ ╱    ← Q4_K_M (sweet spot)
 │╱
 │
 │     Q2 (영어만 살고 한국어는 죽음)
 └─────────────── bit 수
  2    4    8   16
```

4-bit가 경사의 꺾이는 지점이다. 더 줄이면 급격히 나빠지고, 더 늘려도 메모리만 늘고 품질 이득은 적다.

## 6. 내부 동작 — scale과 zero-point

숫자를 낮은 bit로 바꾸는 수식은 생각보다 단순하다.

FP16 weight 한 덩어리가 있다고 하자: `[-0.8, -0.3, 0.1, 0.5, 0.9]`

이걸 4-bit(0~15)로 표현하려면:

1. **범위 찾기**: min = -0.8, max = 0.9
2. **scale 계산**: `scale = (max - min) / 15 ≈ 0.113`
3. **zero-point**: `zp = round(-min / scale) = 7`
4. **양자화**: `q = round(x / scale) + zp`

```
-0.8 → round(-0.8 / 0.113) + 7 = -7 + 7 = 0
-0.3 → round(-0.3 / 0.113) + 7 = -3 + 7 = 4
 0.1 → round( 0.1 / 0.113) + 7 =  1 + 7 = 8
 0.5 → round( 0.5 / 0.113) + 7 =  4 + 7 = 11
 0.9 → round( 0.9 / 0.113) + 7 =  8 + 7 = 15
```

원래 5개의 float가 `[0, 4, 8, 11, 15]`라는 5개의 4-bit 정수가 됐다. `scale`과 `zp`만 같이 저장하면 복원할 수 있다.

**복원(dequantize)**: `x ≈ (q - zp) × scale`

이 매핑이 전체 weight 행렬에 적용된다. 단, 보통 tensor 전체를 하나의 scale로 묶지 않고, **블록 단위(예: 32개 weight마다)로 쪼개서** 각자 다른 scale을 쓴다. 블록마다 분포 특성이 다르니까. `Q4_K_M`의 `K`가 바로 이 block-wise 구조를 뜻한다.

## 7. 단순 rounding은 왜 부족한가 — GPTQ, AWQ

위 수식대로 그냥 round()만 하면 PTQ(Post-Training Quantization)라고 부른다. 빠르지만 품질이 조금 떨어진다. 특히 outlier 때문에.

**문제**: LLM의 activation(중간 계산값)은 소수의 dimension에 outlier가 몰려있다. 그 dimension의 weight를 뭉개면 모델이 확 나빠진다.

**GPTQ**: weight를 하나씩 양자화할 때, 오차를 다음 weight에 보정해서 전파한다. Hessian 행렬로 "어느 weight가 얼마나 중요한지" 계산해서 중요한 건 덜 뭉갠다. 한 줄 요약: *각 weight의 중요도에 가중치를 둔 최소제곱 최적화*.

**AWQ** (Activation-aware Weight Quantization): activation이 크게 나오는 채널은 outlier가 들어오는 지점이다. 그 채널의 weight는 덜 압축한다. 실제 데이터로 activation을 측정해서 "보호할 weight"를 골라낸다.

둘 다 단순 rounding보다 perplexity가 2-3% 낮다. 숫자로는 작아 보이지만, LLM에서 2%는 한국어 "부석사원" vs "경복궁" 정도의 차이다.

## 8. QLoRA — 양자화 + 파인튜닝

여기까지는 "훈련된 모델을 압축해서 돌리는" 얘기였다. QLoRA는 한 걸음 더 간다. **4-bit로 압축된 모델을 그대로 파인튜닝한다.**

```
기존 full 파인튜닝:  30억 파라미터 × 32-bit + 학습 상태 = 48GB+ VRAM
QLoRA:               30억 파라미터 × 4-bit + 작은 LoRA 어댑터 = 6GB
```

비결은:

1. 베이스 모델은 4-bit로 frozen (NF4라는 특수 양자화 포맷)
2. 작은 adapter 행렬만 FP16으로 학습
3. 학습 중 weight는 필요할 때만 dequantize

덕분에 24GB GPU(RTX 3090)로 70B 모델 파인튜닝이 가능해졌다. 개인이 커스텀 LLM을 만드는 시대가 열린 계기다.

## 마무리

양자화를 한 줄로 요약하면: **float를 int로 근사해서 모델을 압축한다.**

그런데 "잘 근사하는 법"이 꾸준히 개선돼서, 지금은 4-bit에서도 영어 기준 원본과 구분이 안 될 만큼 품질이 유지된다. GPTQ/AWQ/K-quants 같은 기법이 그 품질을 지탱한다.

맥북에서 뭐 돌릴지 고민되면 일단 이렇게 시작하자.

```bash
ollama run llama3.2:3b-instruct-q4_K_M
```

그리고 여유되면 Q2와 Q8도 같은 프롬프트로 돌려서 직접 체감해보자. 한국어로 물어보면 차이가 훨씬 빨리 드러난다.
