# 블로그 방향 검토: GitHub Pages 사례

확인일: 2026-11-12. 홈페이지와 글 구조를 비교했다. 아래 평가는 방문자 수나 성능 순위가 아니라, 현재 개인 블로그에 가져올 만한 설계에 대한 판단이다. 이 문서는 검토 자료이며 블로그 글로 발행하지 않는다.

| 사례 | 확인한 구조 | 참고할 점 | 지금 적용할 때의 주의점 |
| --- | --- | --- | --- |
| [Andrej Karpathy](https://karpathy.github.io/) | 날짜·제목·짧은 소개를 한 목록에 표시. 상단 별도 메뉴는 About. | 글을 먼저 보여 주고 종류를 먼저 고르게 하지 않는다. 홈의 기준점으로 가장 적합하다. | 글이 많이 쌓이면 검색·연도별 탐색을 추가할 여지가 있다. |
| [Lil’Log](https://lilianweng.github.io/) | Posts·Archive·Search·Tags·FAQ, 요약 카드, 글별 읽기 시간. [본문 예시](https://lilianweng.github.io/posts/2023-06-23-agent/)에는 목차·도식·참고문헌이 있다. | 홈과 긴 글의 읽기 경험을 나눠 설계한다. 목차와 검색은 글이 늘어난 뒤에도 유용하다. | 지금부터 태그·FAQ를 모두 노출할 필요는 없다. |
| [김정환 블로그](https://jeonghwan-kim.github.io/) | 모든 글을 중심으로 태그·연재·연도 아카이브를 제공한다. | 한글 제목을 읽으며 많은 글을 훑는 방식, 글이 축적됐을 때의 탐색을 참고한다. | 빈 블로그에 많은 태그·연재 메뉴를 미리 만들면 밀도가 과해진다. |
| [Hyperconnect](https://hyperconnect.github.io/) | 제목·작성자·날짜·요약·태그를 반복하는 기술 글 목록. | 긴 제목과 요약의 역할을 명확히 구분한다. | 여러 작성자와 많은 기술 글을 전제로 한 정보량은 개인 블로그에서 줄이는 편이 낫다. |

## 제안

우선 Karpathy처럼 **하나의 글 목록**을 기본으로 하고, Lil’Log에서 **긴 글의 목차·본문·도식·출처 정리**를 참고한다. 글을 쓸 때 에세이/짧은 글/자라는 글 같은 종류를 먼저 선택하지 않는다.

브랜드 이름과 장식보다 먼저 홈에 무엇을 보여 줄지 정한다. 글을 읽는 화면에서는 제목·날짜·요약·본문을 중심으로 삼고, 글쓰기·배포 상태 같은 운영 도구는 작업실에서 찾게 한다. 음악 감상표는 글의 하위 분류가 아니라 독립적으로 쓰는 기능으로 연결할 수 있다.

글이 쌓이기 전에는 분류·태그·시리즈 메뉴를 늘리지 않는다. 연도별 아카이브는 실제 글 수가 늘어났을 때 검토한다. 이번 변경은 기존 글 삭제와 분류 선택 제거에 한정하고, 새 시각 컨셉이나 브랜드는 확정하지 않는다.
